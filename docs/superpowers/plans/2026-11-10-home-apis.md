# home-apis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Go service that serves `/events` (drop-in for the Deno `icloud-calendar-api`), `/solar` (fake data for now) and `/kitchen` (both combined) from one binary in one LXC on `lab`.

**Architecture:** One `net/http` server over two in-memory caches. The calendar cache refreshes from iCloud CalDAV on a TTL and keeps the last good result on errors. The solar cache is filled by a background poller over a pluggable `solar.Source` (only `fake` in this plan). Day grouping and shift are pure functions over expanded occurrences, so nearly all logic is unit-testable without network.

**Tech Stack:** Go 1.24 (stdlib `net/http`, `log/slog`, `encoding/json`), `github.com/emersion/go-webdav/caldav`, `github.com/emersion/go-ical` (+ its `teambition/rrule-go` dependency). Static `CGO_ENABLED=0` linux/amd64 binary, GitHub Actions release, systemd.

**Spec:** `docs/superpowers/specs/2026-11-10-home-apis-design.md` (reference implementation being ported: `~/Repos/github/githendrik/icloud-calendar-api/src/`)

## Global Constraints

- Timezone for all calendar logic: `Europe/Zurich` (configurable `timezone`, default `Europe/Zurich`), never the host TZ.
- `/events` contract: keys and order `today{label,date,events[{summary,start,end,allDay}]}, tomorrow{...}, fetched_at`; labels exactly `"Today"` / `"Tomorrow"`; `json` indented with 2 spaces; timed `start`/`end` as `YYYY-MM-DDTHH:MM:SS` local wall time, no zone suffix; all-day as `YYYY-MM-DD` with exclusive end date; `fetched_at` UTC RFC3339 with milliseconds (`2026-11-10T14:22:03.721Z`).
- Sorting per day: all-day events first, then by `start` ascending; then truncate to `max_events` (default 3).
- Auth: if `api_token` set, every route except `/health` requires `Authorization: Bearer <token>`, else `401 {"error":"Unauthorized"}` — including unknown routes (checked before routing, as in Deno). Unknown route → `404` body `Not Found`.
- Calendar fetch failure with no cached data → `502 {"error":"<message>"}`.
- Config: same JSON keys and env vars as the Deno service (`icloud_username`, `icloud_app_password`, `calendar_name`=`Family`, `port`=3000, `max_events`=3, `cache_ttl_seconds`=300, `api_token`), env overrides file, `--config`/`-c` flag. New keys: `timezone`, `kitchen_max_events`=5, `solar_source`=`fake`, `solar_poll_seconds`=60.
- Solar JSON: `pv_w`, `load_w`, `grid_w` (negative = export), `battery_soc` (0–100), `battery_w` (positive = charging), `updated_at` (UTC RFC3339), `source`, `stale`. Integers for watts and SoC.
- Repo is **public**: no real credentials anywhere; only `deploy/config.example.json`.
- `docs/architecture.md` is updated in every task that changes behaviour (user requirement).

## Review Focus

- DST change days (29 Mar / 25 Oct 2026, 28 Mar 2027): "today"/"tomorrow" boundaries and a 07:00 weekly event must stay 07:00 local → test in Task 2 and Task 3.
- Events stored in UTC (`DTSTART:...Z`) or with a non-Zurich `TZID` must render in Zurich wall time → test in Task 2.
- A recurring series with one moved/cancelled instance (`RECURRENCE-ID`, `EXDATE`) must show the override, not the original, and not both → test in Task 2.
- iCloud outage after a good fetch: `/events` keeps serving the last good data (200), `/health` reports the error → test in Task 4.
- Solar source never fetched yet or failing: `/kitchen` still answers fast with `"solar": null` or `stale: true` → test in Task 5 and Task 6.
